# 缺陷单归档：截图/录屏 → 可直接提交的 Jira 问题单

适用场景：用户发来截图、录屏或一句话现象描述，要求生成可按格式粘贴的 Jira 问题单，或要求直接把问题单提交到 Jira。

本流程与测试用例设计正交：它产出的是缺陷单，不是用例。

## 〇、环境约定来源（先读这一节）

本文件只描述流程，不写站点、项目、经办人、字段 id、目标版本等具体取值；这些属于用户环境约定，按以下顺序解析：

1. 用户当次说明 → 最高优先级
2. 同目录下的本地约定文件 `defect-filing-jira.local.md` → 存在则读取其中的真实取值
3. 两者都没有 → 不要猜，先向用户确认站点、项目、经办人、目标版本后再继续

环境值统一用占位符表示：`<jira-base-url>`、`<project-key>`、`<assignee-user-frontend>`、`<assignee-user-backend>`、`<bug-issue-type>`、`<customfield-id>`、`<version-id>`、`<parent-issue-key>`、`<summary-prefix>`。

本地约定文件属于本机私有内容，不要提交到公开仓库。用户改过约定时以当次说明为准，并提示用户同步更新该文件。

## 一、分析与判定

1. 逐张读附件，不要只看第一张：用本宿主可用的图像理解能力读用户提供的图片（Hermes 下即 `vision_analyze`）。
2. 录屏 GIF 通常只能读到代表帧，无法还原完整点击序列；据此判断不了的部分不要写进单子，或明确让用户补充。
3. 判定归属：
   - 后端：接口报错/超时、服务端校验、路由或资源不存在、返回码异常、服务不可用
   - 前端：渲染、布局、对齐、间距、文案、校验提示、loading、状态刷新、交互反馈、参数未正确提交
   - 两者都有时按主因归类，另一侧只作为现象描述，不武断下结论
4. 不要用界面现象反推根因；能确认到接口/状态码时再写接口层结论。

## 二、会话输出正文（用户直接复制用）

```
【前端】或【后端】问题描述标题（加粗）

前置条件：

1. ...
2. ...

复现步骤：

1. ...

结果：

1. ...

预期结果：

1. ...
```

- 标题后 1 个空行；每个小标题前、后各 1 个空行；末尾不加多余空行
- 四段编号各自从 1 开始，统一 `1. ` 半角句点，禁止 `1，`、禁止跨段连续编号
- 不加表格、代码块、emoji、额外说明；只输出正文
- 描述要求：写清页面模块、具体操作、实际表现、用户影响、可验收的预期结果；前置条件只留必要项

## 三、提交确认（宿主相关，用户通常不愿打字）

正文之后先拿确认，再由用户决定是否提交；用户确认前不要发起任何写操作（建单、上传附件、建链接）。

- Hermes：写一个 HTML 文件，然后单独一行输出 `::preview{file="<绝对路径>"}`，给出 `提交到 Jira` / `先不提交，我要改` / `丢弃` 三个按钮；每个按钮用 `data-hermes-send="..."`，文案要自带单子标识（概要 + 前端/后端 + 附件文件名），这样点击后可直接执行、不依赖上下文；部件不要设背景、字体、外边距，颜色统一用 `var(--accent)`、`var(--border)`、`var(--foreground)`、`var(--muted-foreground)`、`var(--card)`
- 其他宿主（Codex / Claude Code）：不支持交互部件，直接输出正文后用一句话询问「提交到 Jira / 先不提交 / 丢弃」，等用户回复

## 四、提交到 Jira（REST，非 MCP）

`mcp-atlassian` 能读、能建单，但**没有 Jira 附件上传工具**，且 `jira_create_issue` 的 description 会走 Markdown 转换、破坏 ` # ` 列表语法。因此提交走站点 REST v2，用脚本一次跑完。

- 凭据从环境变量 `JIRA_PERSONAL_TOKEN` 读取；Hermes 环境里该变量位于 `~/.hermes/.env`，其他宿主按其 secret 注入机制提供同名变量
- 脚本内用 `os.environ["JIRA_PERSONAL_TOKEN"]` 取值，请求头为 `Authorization: Bearer <token>`
- 不要把 token 打印、回显、写进脚本文件或日志；报错重试时也不要输出完整请求头
- 临时提交脚本写到需求文件夹或系统临时目录，不要落在 skill 包目录内，也不要提交进仓库
- 环境变量缺失或已过期时，告诉用户如何注入，不要退化成把 token 写进脚本

站点与字段取值（真实值来自第〇节的解析顺序）：

| 字段 | 取值 |
|---|---|
| 站点 / 项目 | `<jira-base-url>` / `<project-key>` |
| 项目 / 类型 | `<bug-issue-type>`：部分实例的 Bug 类型名不是「缺陷/Bug」而是自定义名称，建单前必须先确认类型名 |
| 概要 | `<summary-prefix>` + 标题原文，不带【前端】/【后端】 |
| 经办人 | 前端 `<assignee-user-frontend>`；后端 `<assignee-user-backend>`；产品侧或归属不明 `<assignee-user-product>` 兜底；API 传 `{"name":"<assignee-user>"}`，用短用户名而不是邮箱 |
| 故障分类 | `<customfield-id>`：前端 → 页面问题；后端 → 功能问题；产品侧（需要产品定义/决策）→ 需求建议 |
| 影响版本 / 修复的版本 | 用户当次说明的目标版本及其 id `<version-id>`；版本 id 随版本变化，不要固化 |
| 优先级 | 通常必填 |
| Blocks 链接 | 见下方方向说明 |
| 附件 | 通过敏感信息检查后，把用户提供的图片全部上传 |

概要前缀判断顺序：

1. 用户当次明确给出前缀 → 用它
2. 前端问题 → 前端/框架类前缀（`<summary-prefix>`）
3. 后端问题 → 更细的模块名称前缀
4. 兜底：判断不出模块、或用户未明确指出 → 通用兜底前缀

描述用 Jira wiki 语法（与用户历史单保持一致）：

- 小标题单独一行：`前置条件：` / `复现步骤：` / `结果：` / `预期结果：`
- 每个条目行以 ` # ` 开头，Jira 自动渲染成 1. 2. 3.
- 各段之间空一行（`\r\n\r\n`）
- 图片引用 `!文件名.png!` 作为独立条目行，位置在**「预期结果：」之前**（一般放在「结果：」段末）
- dev 与正式环境对比时，先放 dev 图，再插一行 `正式环境`，再放正式环境图
- 接口地址、错误码用 `{{{...}}}` 包裹
- **不要用 `{noformat}`**，会破坏列表渲染

附件：

- 上传前先自查截图内容：出现客户账号、空间 ID、手机号、真实业务数据时，先打码或改为文字描述，并在回报里说明做过哪些脱敏
- 需要时先把图片落盘为文件，再生成文件名 `image-YYYY-MM-DD-HH-MM-SS-mmm.png`，描述里的 `!文件名!` 必须与之一致
- `POST /rest/api/2/issue/{key}/attachments`，multipart/form-data，附加请求头 `X-Atlassian-Token: no-check`

Blocks 链接方向（易错）：

- 用户历史单的结构是 `inward = 新单`、`outward = <parent-issue-key>`，即 `<parent-issue-key>` blocks 新单
- 创建参数：`outwardIssue=<parent-issue-key>`、`inwardIssue=<新单>`，`POST /rest/api/2/issueLink`
- 方向写反的补救：`DELETE /rest/api/2/issueLink/{linkId}` 后按正确参数重建

## 五、回读校验（必做）

用 `GET /rest/api/2/issue/{key}?fields=...&expand=renderedFields` 核对并回报：概要、类型、状态、经办人、优先级、影响版本、修复版本、故障分类、附件文件名与大小、Blocks 链接原始方向（`inward=<新单>`、`outward=<parent-issue-key>`）、描述渲染（有序列表数量、图片在「结果」与「预期结果」之间）。最后把单号与 browse 链接给用户。

回读渲染时的硬要求：`fields` 参数里必须包含 `description`，否则 `renderedFields.description` 返回空，会误判成“列表和图片没渲染”。校验写法：`html.find('结果') < html.find('<img') < html.find('预期结果')`。

链接方向的读法（实测形状，容易看反）：

- GET **新单**时，`issuelinks` 里应出现 `outward_issue = <parent-issue-key>`（该字段名指的是对方所在的一侧），含义是「`<parent-issue-key>` blocks 新单」
- 若 GET 新单时看到 `inward_issue = <parent-issue-key>`，说明方向写反了，按第四节修正

校验不通过时的处置：

- 字段未生效或必填校验失败 → 用 `PUT /rest/api/2/issue/{key}` 补齐后重新回读，不要只回报「已提交」
- 附件缺失 → 重新上传，并以回读到的附件列表为准
- 链接方向反了 → 删链重建
- 单子确实建错（重复单、进错项目）→ 先告知用户并等确认，不要自行删除

最后把单号与 browse 链接给用户。

## 六、常见坑

- 把本站点的 Bug 类型写错（例如写成「缺陷」或「Bug」而实际是自定义名称）→ 建单失败，必须先确认类型名
- `jira_search_assignable_users` 用邮箱查返回 0 条；要用短用户名
- 用 MCP 建单再补描述 → Markdown 转换会让 ` # ` 变成普通文本或段落，列表渲染丢失
- 描述里用 `{noformat}` → 列表和图片都不渲染
- 图片引用写在「预期结果：」之后 → 与用户历史单不一致
- Blocks 方向按文档直觉写 → 与用户其它单不同向；必须以上面实测的 inward/outward 为准
- 没查重就建单 → 用户常已手工提过同一问题，重复单会被打回
- 附件原图含客户账号、空间 ID、手机号 → 上传前必须自查脱敏
- token 未注入或过期 → 建单 401/403；先修环境变量，不要把 token 写进脚本

## 七、执行顺序

1. 读附件 → 2. 判定前后端 → 3. 按概要关键词做一次 JQL 查重（命中则先问用户：改现有单 / 加评论 / 放弃）→ 4. 出正文 → 5. 出确认部件（或文字询问）→ 6. 用户确认 → 7. REST 建单 + 附件 + 链接 → 8. 回读校验 → 9. 回报单号
