# qa-test-design

一个面向需求分析、测试设计、测试用例生成与评审的综合型 QA Skill。

它不是只负责“写几条 case”，而是把以下工作串成一条完整链路：

- 从 PRD / 需求文档 / UI / API / 现有用例中提取测试对象
- 先做可测试性评审，再做测试设计
- 生成测试点、详细测试用例、追溯矩阵、质量风险摘要
- 评审已有测试用例
- 评审 AI 生成的测试产物
- 支持导出为 `xlsx`、`xmind`、`docx`

默认输出格式为 `xlsx`。

---

## 当前默认 xlsx 结构

当前 bundled 脚本默认输出的是轻量三页结构，而不是执行台账增强版：

- 工作表：
  - `概览`
  - `测试用例`
  - `追溯矩阵`

- `测试用例` 页默认列顺序：
  - `用例ID`
  - `模块`
  - `功能/操作`
  - `关联需求`
  - `标题`
  - `前置条件`
  - `步骤`
  - `预期结果`
  - `优先级`
  - `测试类型`
  - `执行角色`
  - `状态`
  - `测试数据`
  - `设计方法`
  - `标签`
  - `备注`

- 内容约定：
  - `步骤` / `预期结果` 在单元格内按多行编号展示
  - `概览` 只承载汇总信息
  - `追溯矩阵` 以需求维度汇总用例列表

如果用户明确要求“执行台账”“按模块拆分执行页”或 `WPS` 条件格式增强，再按需扩展 workbook 结构。扩展规范统一维护在 `references/output-formats.md`。

## 1. 适用场景

适合以下类型的需求：

- 根据需求文档生成测试点或测试用例
- 对已有测试用例做补全、评审、去重
- 为权限复杂、状态复杂、规则复杂的后台系统做系统化测试设计
- 对 AI 生成的测试计划、测试用例、测试报告、需求摘要做质量评审
- 需要追溯矩阵、风险分层、发布前质量判断的场景

尤其适合：

- 用户管理
- 角色管理
- 权限管理
- 组织架构管理
- 管理后台类系统

## 2. 核心能力

### 2.1 可测试性优先

在写测试用例之前，先检查需求是否“可测”：

- 是否可观察
- 是否可控制
- 是否可追溯
- 是否有清晰状态
- 是否有明确权限边界
- 是否有足够的失败和异常定义

### 2.2 测试设计方法内建

按以下顺序组织测试设计：

- 先按不同维度把功能点拆细
- `EP` 等价类划分
- `BVA` 边界值分析
- `ST` 场景法
- `EG` 错误推测

### 2.3 覆盖与去重并重

不仅追求覆盖，还强调：

- 可执行
- 可验证
- 可追溯
- 按验证目标去重，而不是只看标题不同

### 2.4 AI 产物质量评审

对 AI 生成的 QA 产物增加 9 类风险检查：

- 事实性
- 逻辑性
- 语义性
- 来源性
- 指令遵循
- 结构完整
- 上下文保持
- 重复冗余
- 常识文化

- 生成测试点

- 导出 xlsx
- 导出 xmind

支持任意组合：

- API 文档

## 5.1 本地文件夹约定

如果任务依赖本地文件或需要落地产物，这套 skill 默认使用需求文件夹作为任务根目录：

- `./功能需求/`：放需求文档、设计截图、原型导出、流程图等输入材料
- `<当前需求文件夹>/测试用例/`：放测试点、测试用例、追溯矩阵、风险摘要、评审结果等输出材料

禁止把生成的用例文件、追溯矩阵、风险摘要或评审结果写到 `qa-test-design` skill 根目录。

如果目录不存在，优先使用对应脚本自动创建：

- `node scripts/ensure-requirements-folder.mjs`
- `node scripts/ensure-testcases-folder.mjs`

## 6. 主要输出模式

### 6.1 测试点模式

适合先拉广度。

输出内容通常包括：

- 模块拆解
- 细化后的功能点拆解
- 覆盖维度
- 高风险规则
- 优先级建议
- 可测试性问题清单

### 6.2 详细测试用例模式

适合直接进入执行资产沉淀。

每条用例至少包含：

- 用例 ID
- 模块
- 关联需求
- 标题
- 前置条件
- 步骤
- 预期结果
- 优先级
- 类型

生成方式要求：

- 先把收到的功能点按不同维度拆成细小的独立功能点
- 先为每个独立功能点分别生成用例
- 再为功能点之间的关系、依赖、组合、状态衔接、数据联动生成用例
- 每个功能点以及功能点关系都要覆盖相关测试类型，不能只覆盖主流程
- 用例可以逐条生成，也可以按功能点分组生成，但不能草率批量输出

### 6.3 用例评审模式

适合检查已有用例是否存在：

- 漏测
- 重复
- 不可执行步骤
- 不可验证预期
- 缺少需求追溯
- 权限/状态/边界覆盖不足

### 6.4 AI 产物评审模式

适合检查 AI 生成的：

- 测试计划
- 测试用例
- 测试报告
- 需求摘要
- 质量分析文档

### 6.5 追溯与风险模式

适合面向测试管理和发布决策输出：

- 需求到用例追溯矩阵
- 未覆盖需求
- 孤儿用例
- 覆盖率
- 质量风险摘要
- 发布建议

## 8. 导出脚本用法

当前导出脚本优先使用跨平台 Node 版本，兼容 Windows / macOS。

前置条件：

- 已安装 Node.js

### 8.1 生成 xlsx

```bash
node scripts/generate-xlsx.mjs --input <cases.json> --output <output.xlsx> --title <title>
```

### 8.2 生成 xmind

```bash
node scripts/generate-xmind.mjs --input <cases.json> --output <output.xmind> --title <title>
```

### 8.3 生成 docx

```bash
node scripts/generate-docx.mjs --input <cases.json> --output <output.docx> --title <title>
```

输入 JSON 需要是“测试用例数组”。字段不需要完全固定，脚本会尽量兼容这些常见键：

- `case_id` / `id`
- `module` / `模块`
- `feature` / `operation`
- `requirement_id` / `关联需求`
- `title` / `标题`
- `preconditions` / `前置条件`
- `steps` / `步骤`
- `priority` / `优先级`
- `test_type` / `测试类型`
- `design_method` / `设计方法`
- `tags` / `标签`
- `notes` / `备注`

## 9. 这套 skill 的设计原则

### 9.1 不凭空编造需求

如果需求本身没说清楚：

- 会标记为推断或待确认
- 不会假装它已经明确

### 9.1.2 不符合需求就直接失败暴露

这套 skill 在自动化测试用例场景下还有一条更强的约束：

- 所有预期都必须按需求文档和参数定义标准来写
- 如果需求文档或参数定义本身缺失、不完整或有歧义，也必须把问题提出来
- 如果系统执行结果不符合需求定义，就应原样失败暴露出来
- 这种不符合预期的结果应视为 bug，需要被提出
- 不允许为了让测试通过而去修改预期、兼容现状结果、补业务修复逻辑或弱化断言

唯一允许处理的是：

- 测试脚本自身的执行异常
- 环境导致的脚本运行异常

也就是说：

- 业务不符合需求 -> 报失败、提 bug
- 脚本本身跑不起来 -> 处理脚本异常
- 不能为了兼容业务现状去偷偷改测试标准

### 9.1.3 自动化执行遇到异常时的处理规则

这套 skill 现在还要求：

- 先把测试用例完整补齐，再开始自动化执行
- 不允许一边补用例一边执行测试
- 每一步操作前都要先确认页面相关元素和交互状态已经加载完成，再继续执行
- 所有测试项都必须落实到位；如果用例要求点击确认、提交、保存或其他完成动作，就必须真正执行，不能只输入一下就当完成
- 每个测试项执行时都可能遇到页面异常提示、错误弹窗或异常结果，这些都要在脚本中被记录下来
- 一个测试流程完成后不要立刻关闭窗口，至少等待 1 秒，给延迟提示、toast 或校验信息留出暴露时间
- 遇到异常时，要记录真实异常结果并输出到报告中，然后继续执行下一项用例
- 所有用例执行完成后，再统一汇总并分类问题
- 如果同一个自动化执行问题连续排查三轮仍未解决，就应停止继续循环尝试，转而请人工补充缺失的信息、环境细节、权限、测试数据或期望行为后再继续

只有一种情况可以中断流程：

- 测试脚本自身已经无法继续执行

另外，如果执行过程中发现需求、参数定义、断言基线本身可能有问题：

- 先罗列问题
- 先请示人工
- 获得同意后再修改用例或规则

### 9.1.4 自动化执行前先最大化窗口

这套 skill 现在还要求：

- 凡是浏览器页面型自动化执行，都要先最大化窗口，或设置足够大的视口
- 这样做是为了避免页面元素因为窗口太小而不可见、被折叠、被遮挡或被裁切
- 如果元素定位失败，先检查并修正窗口/视口状态，再判断是否为真实业务问题

也就是说：

- 小窗口导致看不见元素 -> 先调整窗口，不直接判业务失败
- 窗口正常后仍异常 -> 再按真实缺陷处理

### 9.2 权限域优先考虑后端拦截

在用户/角色/权限类系统里，必须区分：

- 前端是否展示按钮
- 后端是否真正拦截越权操作

这两个不是同一个测试点。

### 9.3 先判断“验什么”，再决定“写几条”

去重的核心标准不是标题，而是验证目标。

进一步说：

- 先拆功能点，再写用例
- 先写单点验证，再写点与点之间的关系验证
- 先确认覆盖了哪些测试类型，再决定还缺哪些用例

### 9.4 测试不是只为执行，也为决策服务

这套 skill 不只生成 case，也希望输出：

- 风险判断
- 覆盖全景
- 发布前建议

## 10. 建议的使用顺序

对较完整的需求，建议按下面顺序使用：

1. 先做可测试性检查
2. 再做测试点清单
3. 再做详细测试用例
4. 再补追溯矩阵
5. 最后补质量风险摘要

对于 AI 产物，则建议：

1. 先做结构完整性检查
2. 再做 9 类幻觉风险评审
3. 再判断它能否直接用于执行或仅能作为草稿

## 12. 后续怎么迭代

这份 skill 设计成可长期演进，建议按下面方式继续优化：

### 12.1 迭代业务规则库

优先补：

- 用户管理
- 角色管理
- 权限管理
- 组织架构
- 审批流
- 数据权限

### 12.2 迭代 few-shot

把你团队里“好输出”和“坏输出”的真实例子不断补到 `few-shot-examples.md`。

### 12.3 迭代导出脚本

当前脚本已经能生成三种格式，但后面还可以继续增强：

- 更丰富的 xlsx 工作表
- 更漂亮的 docx 样式
- 更细的 xmind 节点结构
- 统一入口脚本

### 12.4 迭代字段映射兼容性

如果你们团队 JSON 字段命名更固定，可以继续扩展 `scripts/common.mjs` 里的字段映射逻辑。

### 12.5 每次使用后的自动补强

### 12.6 Skill 的自我学习与进化

这套 skill 现在被定义为“可学习、可进化”的 skill：

- 它可以从每次真实任务中总结新的规则、案例模式、领域知识、输出规范和踩坑经验
- 但这些新知识不能自动入库
- 每次都必须先向人工展示“建议补充到 skill 的内容”
- 只有在人工确认后，才允许写入 `SKILL.md` 或 `references/`，成为 skill 后续可调用的知识库

也就是说，这个 skill 允许自我进化，但不允许绕过人工审核直接进化。

### 12.7 输出文件落地规则

这套 skill 现在还要求：

- 最终生成的用例、追溯矩阵、风险摘要、评审结果等交付件，默认必须落在当前需求文件夹目录下的 `测试用例/`
- 可以使用临时目录做中间处理，但不能只把结果留在临时目录里
- 如果用户没有指定目录，不要把最终文件放到别的路径
- 不允许把最终交付件写到 `qa-test-design` skill 根目录
- 文档写入后必须检查中文标题、工作表名、字段名和正文是否乱码；有乱码就不能交付
- 最终说明中要明确告知已完成无乱码检查
- 处理包含中文路径、中文工作表名、中文单元格或正文内容的文档/工作簿时，不要用 PowerShell heredoc、命令行内联长脚本或长字符串拼接生成文件；应先写入独立 UTF-8 脚本，再执行脚本并回读校验
- 如果必须维护 Windows PowerShell 辅助脚本且脚本内含中文文本，脚本文件使用 UTF-8 with BOM；Node/Python 辅助脚本使用 UTF-8，并优先通过 `workdir + 文件名` 处理中文路径


这套 skill 现在还有一条持续迭代守则：

- 每次实际使用完 skill 后，都要回看这次过程中出现了哪些修正、补充、漏项或新的稳定模式
- 如果这些内容具有复用价值，而当前 skill 里还没覆盖，就要及时补回 skill 包本身

补充原则：

- 核心工作流和硬规则，补到 `SKILL.md`
- 领域规则、输出样式、案例模式、格式约束，补到 `references/`

这样做的目的，是让 skill 越用越完整，而不是把新知识只留在某次对话里。

## 文档读取脚本

如果输入是文件而不是直接粘贴的文本，优先先用统一脚本抽取全文，再继续做测试设计。

```bash
node scripts/read-document.mjs --input <source-file> --output <text-file>
```

支持或适配的格式包括：

- `html` / `htm`
- `doc` / `docx`
- `pdf`
- `rtf`
- `txt` / `md` / `json` / `csv` 等纯文本格式

平台说明：

- Windows 下 `doc/docx/pdf/rtf` 通过 `read-document-win.ps1` 调用本地 Word COM 读取
- macOS 下 `doc/docx/rtf/html` 优先走 `textutil`
- macOS / Linux 下 `pdf` 优先尝试 `pdftotext`，其次 `mutool`

这条脚本的目的，是把“完整读取文档”的动作标准化，避免只靠人工临时抽取正文。

## JSON -> XLSX 一键脚本

如果你的用例先以原始 JSON 形式产出，推荐直接使用下面这条脚本完成“结构化 JSON 落地 + xlsx 导出”两步：

```bash
node scripts/generate-json-and-xlsx.mjs --input <raw-cases.json> [--output-dir <dir>] [--base-name <name>] [--title <title>]
```

作用：

- 读取原始 case JSON
- 归一化成标准结构化 JSON
- 先把标准 JSON 落到最终输出目录
- 再自动导出对应的 xlsx

如果不传 `--output-dir`，默认输出到当前需求文件夹目录下的 `测试用例/`。
